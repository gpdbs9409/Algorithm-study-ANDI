## 1. 문제

각 기능은 진도가 100%에 도달해야 배포할 수 있다.

모든 기능은 동시에 개발되지만, 배포는 정해진 순서대로 이루어진다.

뒤에 있는 기능이 먼저 완성되더라도 앞에 있는 기능이 완성될 때까지 기다려야 한다.

각 배포마다 몇 개의 기능이 배포되는지 반환하는 문제이다.

### 입출력 예시

| progresses | speeds | return |
|---|---|---|
| [93, 30, 55] | [1, 30, 5] | [2, 1] |
| [95, 90, 99, 99, 80, 99] | [1, 1, 1, 1, 1, 1] | [1, 3, 2] |

## 2. 접근

### 접근 1. Queue를 사용한 이유

- Stack은 나중에 들어온 원소를 먼저 꺼낸다. (LIFO)
- Queue는 먼저 들어온 원소를 먼저 꺼낸다. (FIFO)

기능개발 문제에서는 반드시 앞에 있는 기능부터 배포해야 하므로 Queue가 적절하다.(순서가 앞선 기능이 먼저 배포된다.) 
이를 위해 다음 변수가 필요하다고 판단했다.

- `cur`: 각 기능의 현재 진행률
- `stack`: 완료된 기능을 저장
- `num`: 한 번에 배포되는 기능 개수
- `answer`: 배포 결과

또한 처음에는 하루씩 진행률을 갱신하려고 했다.
i day가 지나면 계속 진행률을 갱신하는 방식이다.->이렇게 진행률이 100퍼센트가 되면 배포가능한 상태로 플래그를 달아주고, 플래그가 True이면 배포하는 방식으로 하면 되겠지? 라는 생각이었다. 

```python
cur[i] += speeds[i]
```




## 3. Sol1 - 접근 1에 따른 풀이

처음 생각했던 하루 단위 진행률 갱신 방식을 코드로 구현하면 다음과 같다.

```python
def solution(progresses, speeds):
    cur = progresses[:]
    stack = []
    answer = []

    while cur:
        # 하루 동안 모든 기능의 진행률 갱신
        for i in range(len(cur)):
            cur[i] += speeds[i]

        # 앞에서부터 배포 가능한 기능 확인
        num = 0

        while cur and cur[0] >= 100:
            stack.append(cur.pop(0))
            speeds.pop(0)
            num += 1

        if num > 0:
            answer.append(num)

        stack.clear()

    return answer
```

이 코드는 하루씩 진행률을 갱신하는 시뮬레이션 방식이다.



### 접근 2. 완료일을 이용한 배포

다시 생각해 보니 `days` 배열만 있으면 현재 진행률을 갱신할 필요가 없었다.

각 기능이 언제 완료되는지 이미 알고 있기 때문이다.

따라서 다음과 같이 접근했다.

1. 각 기능이 완료되기까지 필요한 날짜를 계산한다.
2. 완료일을 Queue에 저장한다.
3. Queue의 가장 앞에 있는 완료일을 현재 배포 기준일로 설정한다.
4. 기준일보다 완료일이 작거나 같은 기능은 함께 배포한다.
5. Queue에서 기능을 꺼낼 때마다 `num += 1`로 개수를 센다.
6. 하나의 배포 묶음이 끝나면 `answer`에 `num`을 추가한다.
7. Queue가 빌 때까지 반복한다.

예를 들어 다음과 같다.

```python
days = [7, 3, 9, 5, 4]
```

첫 번째 배포 기준일은 7이다.

```text
[7, 3] | [9, 5, 4]
```

3일 걸리는 기능은 7일째 이미 완료되어 있으므로 함께 배포할 수 있다.

다음 기능은 9일이 걸리므로 새로운 배포 기준일은 9가 된다.

```text
[7, 3] | [9, 5, 4]
   2          3
```

따라서 결과는 다음과 같다.

```python
answer = [2, 3]
```

## 4. Sol2 - Queue를 이용한 풀이

```python
from collections import deque

def solution(progresses, speeds):
    days = deque()
    answer = []

    # 각 기능의 완료일 계산
    for i in range(len(progresses)):
        day = math.ceil((100 - progresses[i]) / speeds[i]) #올림하는 함수
        days.append(day)

    # Queue가 빌 때까지 배포
    while days:
        standard = days.popleft()
        num = 1

        # 현재 기준일 안에 완료되는 기능들을 함께 배포
        while days and days[0] <= standard:
            days.popleft()
            num += 1

        answer.append(num)

    return answer
```

## 5. 틀린 이유 및 배운 점

### 1. 접근법을 변경했지만 기존 로직을 제거하지 않았다.

처음에는 매일 진행률을 갱신하는 시뮬레이션 방식을 생각해 `cur` 배열을 만들었다.

이후 각 기능의 완료일을 미리 계산하는 `days` 배열을 떠올렸지만, 기존 `cur` 갱신 로직을 그대로 유지하려고 했다.

그러나 완료일을 알고 있다면 현재 진행률을 별도로 계산하지 않아도 완료 여부를 판단할 수 있다.

즉, `days`를 도입한 순간 `cur`의 역할이 불필요해진 것이다.

**교훈:** 새로운 변수나 접근법을 도입할 때 기존 변수의 역할이 여전히 필요한지 확인하자. 특히 접근법을 바꿨다면 기존 수도코드에 덧붙이지 말고 처음부터 다시 정리하자.

### 2. 자료구조를 선택하는 기준이 명확하지 않았다.

처음에는 완료된 기능들을 쌓아 두었다가 한 번에 꺼내야 한다는 생각으로 Stack을 선택했다.

하지만 중요한 것은 데이터를 쌓는 행위 자체가 아니라, 어떤 순서로 꺼내야 하는지였다.

이 문제는 먼저 들어온 기능부터 배포해야 하므로 FIFO 구조인 Queue가 더 적절하다.

### 3. 문제에서 실제로 필요한 정보가 무엇인지 구분하지 못했다.

처음에는 각 기능의 현재 진행률을 계속 알아야 한다고 생각했다.

하지만 문제에서 필요한 것은 매일의 진행률이 아니라 각 기능의 완료일과 배포 순서였다.

따라서 모든 상태를 시뮬레이션하지 않고, 필요한 정보만 계산해서 문제를 해결할 수 있었다.

**교훈:** 구현 전에 문제의 최종 목표를 확인하고, 그 목표를 판단하는 데 필요한 최소한의 정보가 무엇인지 생각하자.

## 6. 시간 / 공간복잡도


시간복잡도는 O(n)이다. 
=> 첫번째 while days:에서 계속 원소가 제거된다. 그리고 내부에 while이 하나 더 있긴하지만 n이 n만큼 최대 중복되는 것이아니라 , 각 원소에 대한 계산은 한번만 일어난다.. 


공간복잡도는 days배열만큼 n만큼의 공간만 필요하고 추가적으로 필요하지않으므로
O(n)이다.
