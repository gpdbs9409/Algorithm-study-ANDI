# 연속된 부분 수열의 합

## 1. 문제

비내림차순으로 정렬된 수열 `sequence`와 정수 `k`가 주어진다.

다음 조건을 만족하는 연속 부분 수열을 찾아 시작 인덱스와 마지막 인덱스를 반환해야 한다.

1. 부분 수열의 합은 `k`여야 한다.
2. 합이 `k`인 부분 수열이 여러 개라면 길이가 가장 짧은 수열을 선택한다.
3. 길이까지 같다면 시작 인덱스가 가장 작은 수열을 선택한다.

---

## 2. 접근 1. 누적합 + 완전탐색

처음에는 배열에서 부분합을 구해야 하므로 **누적합 문제**라고 판단했다.

### 접근 과정

1. 원본 배열 외에 누적합 배열 `sum_list`를 생성한다.
2. `sum_list`에는 0번부터 n번 인덱스까지의 누적합을 저장한다.
3. 이중 `for`문을 이용해 가능한 모든 구간 `(i, j)`를 확인한다.
4. `sum_list[j] - sum_list[i] == k`인 경우 해당 구간을 후보 배열 `temp`에 저장한다.
5. 후보 중 구간의 길이가 가장 짧은 것을 선택한다.
6. 길이가 같은 후보가 여러 개라면 시작 인덱스 `i`가 가장 작은 것을 선택한다.

### 필요한 변수

- `sum_list`: 누적합을 저장하는 배열
- `temp`: 합이 `k`인 구간의 후보를 저장하는 배열
- `answer`: 최종 정답

### 한계

누적합을 사용하면 구간 합을 O(1)에 구할 수 있다.

하지만 이중 `for`문으로 모든 `(i, j)` 조합을 확인해야 하므로 전체 시간복잡도는 **O(n²)**이다.

---

## 3. 접근 2. 슬라이딩 윈도우 (투 포인터)

접근 1에서는 누적합을 구한 뒤 완전탐색을 수행하므로 시간복잡도가 O(n²)이 된다.

하지만 **슬라이딩 윈도우(투 포인터)**를 사용하면 모든 `(i, j)` 조합을 확인하지 않아도 되므로 시간복잡도를 줄일 수 있다.

특히 수열이 오름차순 또는 내림차순으로 정렬되어 있다면 이러한 접근을 떠올리기 좋다.

### 3-1. 누적합 배열이 꼭 필요할까?

생각해 보니 누적합을 따로 구할 필요도 없다.

현재 구간의 합만 `current_sum`으로 관리하면 되기 때문이다.

포인터가 이동할 때마다 다음과 같이 처리할 수 있다.

- 오른쪽 포인터 이동: 새로 포함되는 원소를 더한다.
- 왼쪽 포인터 이동: 구간에서 제외되는 원소를 뺀다.

즉, **이전에 계산한 구간 합을 재활용하는 방식**이다.

### 3-2. 누적합을 사용하지 않는 이유

누적합 배열을 만든다고 하더라도 투 포인터를 사용하면 시간복잡도는 O(n)으로 동일하다.

하지만 누적합 배열을 따로 선언하지 않으면 공간복잡도를 줄일 수 있다.

또한 생각해 보면 누적합은 구간 합을 여러 번 구해야 할 때 더 의미가 있다.

반면 이번 문제에서는 현재 탐색 중인 구간의 합 하나만 관리하면 된다.

따라서 누적합 배열을 만드는 것은 약간 오버스펙이라는 생각이 들었다.

### 3-3. 최종 접근 방향

접근 1과 비교하면 다음과 같이 개선하는 것이다.

| 구분 | 접근 1 | 접근 2 |
|---|---|---|
| 구간 합 계산 | 누적합 배열 | 현재 합을 직접 갱신 |
| 구간 탐색 | 이중 for문 | 슬라이딩 윈도우 (투 포인터) |
| 시간복잡도 | O(n²) | O(n) |
| 추가 공간복잡도 | O(n) | O(1) |

**핵심은 구간을 한 칸씩 이동하면서 기존 합을 재활용하는 것이다.**

포인터가 일정한 방향으로 이동한다는 점을 고려하면, 모든 구간을 처음부터 다시 계산할 필요가 없다.

---

## 4. Sol 


```python

def solution(sequence, k):
    left = 0
    current_sum = 0
    answer = [0, len(sequence) - 1]

    for right in range(len(sequence)):
        current_sum += sequence[right]

        while current_sum >= k:
            if current_sum == k:
                if right - left < answer[1] - answer[0]:
                    answer = [left, right]

            current_sum -= sequence[left]
            left += 1

    return answer
```

## 5. 배운 점

### 5-1. 누적합은 언제 필요한가?

처음에는 부분합을 구해야 한다는 이유만으로 누적합을 떠올렸다.

하지만 누적합이 항상 필요한 것은 아니다.

**여러 구간의 합을 반복적으로 조회해야 할 때** 누적합이 특히 유용하다.

반면 현재 구간을 한 칸씩 이동하면서 합을 관리할 수 있다면, 기존 합에서 원소를 더하거나 빼는 방식으로도 충분하다.

### 5-2. 투 포인터를 이용하면 시간복잡도를 줄일 수 있다

이중 `for`문으로 모든 구간을 확인하면 O(n²)이 된다.

하지만 투 포인터를 이용하면 현재 합과 `k`를 비교하면서 필요한 방향으로 포인터를 이동할 수 있다.

따라서 불필요한 구간 탐색을 생략할 수 있다.

### 5-3. 기존 계산 결과를 재활용할 수 있는지 생각하기

구간이 한 칸씩 이동할 때마다 합을 처음부터 다시 계산할 필요는 없다.

이전 구간의 합에서 빠지는 원소를 빼고, 새로 들어오는 원소를 더하면 된다.

**특히 구간이 일정한 방향으로 이동하는 문제에서는 기존 값을 재활용할 수 있는지 먼저 생각해 보자.**

## 6. 시간 / 공간복잡도

### 시간복잡도: O(n)

슬라이딩 윈도우를 사용하면 두 포인터가 배열을 한 방향으로 이동한다.

따라서 배열을 한 번 훑는 방식으로 탐색할 수 있으므로 시간복잡도는 O(n)이다.

### 공간복잡도: O(1)

누적합 배열을 별도로 생성하지 않는다.

현재 구간의 합과 두 포인터 등 일정한 개수의 변수만 사용한다.

따라서 입력 배열 외에 필요한 추가 공간은 O(1)이다.

※ 위 복잡도는 접근 2에서 의도한 슬라이딩 윈도우 알고리즘 기준이며, 초기 코드의 실제 동작을 분석한 결과는 아니다.
