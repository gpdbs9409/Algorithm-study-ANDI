# 주사위 고르기 (프로그래머스 Lv.3)

- 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/258709

## 0. 문제 요약

`n`개의 주사위 중 A가 `n/2`개를 고르고, B는 나머지를 가져간다. 각자 고른 주사위를 모두 굴려 나온 수의 합으로 승부하며, 합이 같으면 무승부다. **A의 승리 확률이 가장 높은 주사위 조합**을 번호 오름차순으로 반환한다.

주사위는 최대 10개이고 각 주사위에는 6개의 면이 있다. 같은 주사위에 같은 숫자가 여러 번 적혀 있을 수도 있다.

## 사용 알고리즘 / 자료구조

- 조합, DFS(재귀), 정렬, 이분 탐색

## 1. 문제 접근

먼저 A가 가져갈 `n/2`개 주사위의 **조합**을 고른다. `n = 4`라면 `4C2 = 6`가지다. A가 고르지 않은 주사위는 자동으로 B의 것이므로 B의 조합은 따로 만들지 않는다.

처음에는 A의 합을 정한 뒤 B의 주사위 면 인덱스들을 곱해 승수를 계산할 수 있을지 생각했다. 하지만 B의 한 주사위에서 어떤 면을 골랐는지에 따라 다른 주사위에서 이길 수 있는 면의 개수가 달라진다. 단일 인덱스 곱으로 전체 승수를 나타내기보다는 **각 면 조합에서 나오는 합**을 세어야 한다. 같은 숫자가 여러 면에 적혀 있다면 같은 합도 여러 번 나올 수 있는데, 이 역시 서로 다른 경우의 수다.

한 조합의 승수는 다음 순서로 계산한다.

```text
A가 고른 주사위의 모든 합 생성
B가 고른 주사위의 모든 합 생성
→ A의 합 하나마다, 그보다 작은 B의 합이 몇 개인지 세기
→ 모든 A의 합에 대한 승수 누적
```

어떤 주사위 조합이든 전체 승부 경우의 수는 `6ⁿ`으로 같다. 따라서 확률의 분모를 계산하지 않고 **승리 횟수만 비교**하면 된다.

주사위가 최대 10개라서 한쪽의 합은 최대 `6⁵ = 7,776`개다. A와 B의 모든 합을 이중 반복문으로 비교하면 한 조합에서 약 `6.0 × 10⁷`번, 전체 조합에서 약 `1.52 × 10¹⁰`번 비교해야 한다. 이를 줄이기 위해 B의 합을 정렬하고, A의 합보다 작은 B의 합의 개수를 이분 탐색으로 구했다.

## 2. 문제 코드

```java
import java.util.*;

class Solution {
    public int[] solution(int[][] dice) {
        int[] answer = {};

        List<int[]> combA = new ArrayList<>();
        choose(0, 0, dice.length, new int[dice.length / 2], combA);

        int maxWins = -1;
        for (int[] a : combA) {
            boolean[] selected = new boolean[dice.length];
            for (int index : a) {
                selected[index] = true;
            }

            int[] b = new int[a.length];
            int bIndex = 0;
            for (int i = 0; i < dice.length; i++) {
                if (!selected[i]) {
                    b[bIndex++] = i;
                }
            }

            List<Integer> sumsA = sumDice(dice, a);
            List<Integer> sumsB = sumDice(dice, b);

            int wins = countWins(sumsA, sumsB);

            if (wins > maxWins) {
                maxWins = wins;
                answer = a.clone();
            }
        }

        for (int i = 0; i < answer.length; i++) {
            answer[i]++;
        }

        return answer;
    }

    int countWins(List<Integer> sumsA, List<Integer> sumsB) {
        Collections.sort(sumsB);
        int wins = 0;

        for (int a : sumsA) {
            int left = 0;
            int right = sumsB.size();

            while (left < right) {
                int mid = (left + right) / 2;
                if (sumsB.get(mid) < a) {
                    left = mid + 1;
                } else {
                    right = mid;
                }
            }

            wins += left;
        }

        return wins;
    }

    List<Integer> sumDice(int[][] dice, int[] index) {
        List<Integer> sums = new ArrayList<>();
        makeSums(dice, index, 0, 0, sums);
        return sums;
    }

    void makeSums(int[][] dice, int[] index, int i,
                  int sum, List<Integer> sums) {
        if (i == index.length) {
            sums.add(sum);
            return;
        }

        int diceIdx = index[i];
        for (int num : dice[diceIdx]) {
            makeSums(dice, index, i + 1, sum + num, sums);
        }
    }

    void choose(int start, int count, int n,
                int[] picked, List<int[]> comb) {
        if (count == picked.length) {
            comb.add(picked.clone());
            return;
        }

        for (int i = start; i < n; i++) {
            picked[count] = i;
            choose(i + 1, count + 1, n, picked, comb);
        }
    }
}
```

### 코드 구현 흐름

| 순서 | 함수·코드 | 역할 |
| --- | --- | --- |
| 1 | `choose()` | A가 가져갈 `n/2`개 주사위의 조합을 만든다. |
| 2 | `solution()`의 `selected`, `b` | A가 선택하지 않은 주사위를 B에게 배정한다. |
| 3 | `sumDice()` → `makeSums()` | 각 주사위에서 면 하나씩 고른 모든 합을 A와 B에 대해 각각 만든다. |
| 4 | `countWins()` | A의 합보다 작은 B의 합 개수를 세어 승수를 구한다. |
| 5 | `solution()`의 `wins > maxWins` | 지금까지 승수가 가장 큰 A의 조합을 저장한다. |
| 6 | 마지막 `for`문 | 0부터 시작하는 인덱스를 1부터 시작하는 주사위 번호로 바꾼다. |

## 3. 새롭게 배운 내용

### 조합: 왜 `i + 1`부터 다음 주사위를 고를까?

`n = 4`일 때 `choose()`가 만드는 선택은 인덱스 기준 `[0,1]`, `[0,2]`, `[0,3]`, `[1,2]`, `[1,3]`, `[2,3]`이다. `[0,1]`과 `[1,0]`은 같은 주사위를 고른 것이므로 하나만 필요하다. 다음 주사위를 항상 이전보다 뒤에서 고르는 `choose(i + 1, ...)`가 순서만 다른 중복을 막는다.

완성된 `picked`는 `clone()`으로 복사해 저장한다. 복사하지 않으면 리스트의 항목들이 재귀 중 계속 바뀌는 **같은 배열**을 참조한다.

### B는 A의 선택에 대한 여집합이다

```text
전체 인덱스: [0, 1, 2, 3]
A의 선택:   [0, 2]
B의 선택:   [1, 3]
```

`selected[index] = true`로 A의 주사위를 표시하고, 표시되지 않은 인덱스를 `b`에 넣는다. A가 이미 절반을 골랐으므로 B의 조합을 또 생성할 필요가 없다.

### DFS: 한 조합에서 모든 합을 만드는 방법

`makeSums()`의 `i`는 **몇 번째로 선택한 주사위의 면을 고르는 중인지** 나타낸다. 현재 주사위의 여섯 면을 차례로 시도하며 `sum + num`을 전달한다. `i == index.length`가 되면 모든 주사위에서 면을 하나씩 골랐으므로 합을 저장한다.

같은 값이 여러 면에 있거나 다른 면 조합에서 같은 합이 나오더라도 `sums`에 각각 저장한다. 값은 같아도 **서로 다른 면 조합은 서로 다른 승부 경우의 수**다.

### 이분 탐색: 왜 `wins += left`일까?

`countWins()`는 정렬된 B의 합에서 **A의 합 `a` 이상인 값이 처음 나오는 위치**를 찾는다. 그 위치보다 앞에 있는 값들은 전부 `a`보다 작아 A가 이긴다.

```text
정렬된 B의 합: [2, 5, 5, 8]
A의 합: 6

인덱스:         0  1  2 | 3
B의 합:         2  5  5 | 8
A=6의 결과:     승 승 승 | 패
                        ↑
                      left=3
```

`left = 3`은 **처음으로 이기지 못하는 위치**다. 그 앞의 인덱스 `0`, `1`, `2`에 세 값이 있으므로 `wins += left`가 곧 3승을 더하는 연산이다. `left`는 A의 합 하나마다 0으로 다시 시작하고, 탐색이 끝난 뒤 **한 번만** `wins`에 더한다.

- A의 합이 `5`라면 `[2 | 5, 5, 8]`이므로 `left = 1`, 1승이다. 같은 `5`는 무승부다.
- A의 합이 `1`이라면 `left = 0`, 0승이다.
- A의 합이 `9`라면 전부 이기므로 `left = 4`, 4승이다.

탐색 중 `sumsB.get(mid) < a`라면 `mid`와 그 앞의 값들은 모두 `a`보다 작으므로 다음 후보는 `mid + 1`부터다. 반대로 `sumsB.get(mid) >= a`라면 `mid`가 첫 경계일 수도 있어 `right = mid`로 둔다. **`left = mid + 1` 자체가 승수를 더하는 것이 아니라**, 최종 경계 위치를 찾아 가는 과정이다.

### 인덱스를 실제 주사위 번호로 바꾸기

배열 인덱스는 0부터, 문제의 주사위 번호는 1부터 시작한다. `choose()`가 인덱스를 오름차순으로 고르므로 마지막에 각각 1을 더하면 요구한 번호 오름차순의 답이 된다.

## 4. 처음 보는 문제에서의 사고 흐름

### “A가 `n/2`개를 고른다” → 왜 조합일까?

먼저 **고르는 순서가 결과를 바꾸는지** 확인한다. 1번과 3번을 고른 결과는 3번과 1번을 고른 결과와 같다. 순열로 순서까지 구분하면 같은 선택을 여러 번 계산하므로 조합으로 A의 선택을 만든다. B는 남은 주사위를 전부 가져가니 A의 여집합으로 정한다.

### “고른 주사위를 모두 굴려 합한다” → 왜 DFS일까?

주사위마다 여섯 면 중 하나씩 골라야 **합 하나**가 완성된다.

```text
첫 번째 주사위의 면 선택
  → 두 번째 주사위의 면 선택
    → 세 번째 주사위의 면 선택
      → ... → 선택한 숫자의 합 저장
```

주사위가 항상 2개라면 이중 `for`문으로도 가능하다. 하지만 A가 고르는 개수는 입력에 따라 1~5개로 달라진다. 개수마다 중첩 반복문을 따로 작성하는 대신 **면 하나 선택 → 다음 주사위로 이동**을 재귀 함수로 반복한다. 한 선택을 끝까지 따라갔다가 다음 면을 시도하므로 DFS 형태가 된다. 그래프 문제라서 DFS를 고른 것이 아니라, **단계 수가 달라지는 모든 선택을 만들어야 해서** 선택한 것이다.

### “A의 합이 B의 합보다 커야 한다” → 왜 이분 탐색일까?

가장 단순하게는 A의 합 하나를 B의 모든 합과 비교할 수 있다. 그러나 최대 입력에서 양쪽 합이 각각 `7,776`개이고 A의 조합도 `252`개여서 전체 비교가 약 `1.52 × 10¹⁰`번이 된다.

필요한 값을 다시 생각해 보면, A의 합 `a`마다 **B의 합 중 `a`보다 작은 값의 개수**만 알면 된다. B의 합을 정렬하면 작은 값은 앞쪽에 연속해 모인다. 따라서 “처음으로 `a`보다 작지 않은 위치”라는 **경계 하나**를 찾으면, 그 앞의 원소 개수가 승수다. 정렬된 목록에서 이런 경계를 빠르게 찾는 방법으로 이분 탐색을 선택했다.

이분 탐색만 가능한 것은 아니다. A와 B의 합을 모두 정렬해 투 포인터로 셀 수도 있다. 현재 코드는 **B 목록을 한 번 정렬하고, A의 합마다 경계를 찾는 방식**이다.

### “승리 확률이 가장 높아야 한다” → 왜 승수만 비교할까?

A가 어느 조합을 고르든 모든 주사위의 면을 선택하는 전체 경우의 수는 `6ⁿ`으로 같다. 확률의 분모가 모든 조합에서 같으므로 **승리 횟수만 비교**해도 승리 확률이 가장 높은 조합을 찾을 수 있다.

이처럼 문제를 처음 읽을 때는 **무엇을 고르는가 → 고른 것에서 어떤 결과가 나오는가 → 결과를 어떻게 비교하는가**로 나누고, 각 단계에서 단순한 방법이 가능한지부터 확인하면 알고리즘 선택의 이유가 보인다.

## 5. 시간복잡도 / 공간복잡도

A가 고르는 주사위 수를 `m = n/2`, A의 조합 수를 `C = nCm`, 한쪽이 만들 수 있는 합의 개수를 `S = 6ᵐ`이라고 하자.

- A의 주사위 선택은 `C`가지다.
- 각 선택에서 A와 B의 합을 각각 `S`개 만들고, B의 합을 정렬한 뒤 A의 합마다 이분 탐색한다.
- **전체 시간복잡도: `O(C × S log S)`**.
- **공간복잡도: `O(C × m + S)`** — 저장한 A 조합과 현재 두 합 목록에 필요한 공간이다.

최대 조건 `n = 10`일 때 `C = 10C5 = 252`, `S = 6⁵ = 7,776`, `log₂ S ≈ 13`이다. `C × S × log₂ S ≈ 2.5 × 10⁷`은 규모를 가늠하는 값이며, 정렬과 합 생성의 실제 연산이 더해진다. 그래도 모든 합의 쌍을 직접 비교하는 약 `1.52 × 10¹⁰`번보다 훨씬 적다. 흔히 쓰는 `10⁸` 기준도 실제 실행 시간을 보장하는 숫자가 아닌 대략적인 판단 기준이다.

## 6. 엣지 케이스

- 같은 합이 여러 번 나와도 서로 다른 면 조합이라면 각각 저장하고 센다.
- A와 B의 합이 같으면 **무승부**이므로 `B의 합 < A의 합`만 승수에 넣는다.
- 어떤 선택의 승수가 0이어도 첫 선택을 저장할 수 있도록 `maxWins = -1`로 시작한다.
- 최종 답은 0부터 시작하는 배열 인덱스가 아니라 1부터 시작하는 주사위 번호다.
- 한 조합에서 가능한 최대 승수는 `7,776² = 60,466,176`으로 `int` 범위 안에 있다.

## 7. 한줄평

한 번에 구현하려니 어려웠지만, **조합으로 선택하기 → DFS로 합 만들기 → 이분 탐색으로 승수 세기**로 나누니 각 함수가 해야 할 일이 분명해졌다.

## 8. 더 나은 풀이와 코드 개선

현재 코드는 전체 작업을 함수별로 분리했고, 모든 A·B 합을 직접 비교하지 않아 코딩테스트용으로 충분히 좋다. 더 읽기 쉽게 하려면 `a`와 `b`를 `selectedA`, `selectedB`로, `makeSums()`의 `i`를 `depth`로 바꿀 수 있다. 다만 알고리즘이나 성능이 달라지는 수정은 아니다.

승수 계산에는 **투 포인터**도 사용할 수 있다. A와 B의 합을 모두 정렬한 다음, A의 합을 작은 것부터 보면서 `B의 합 < A의 합`을 만족하는 B의 경계를 오른쪽으로만 이동한다.

```java
Collections.sort(sumsA);
Collections.sort(sumsB);

int bIndex = 0;
int wins = 0;
for (int aSum : sumsA) {
    while (bIndex < sumsB.size() && sumsB.get(bIndex) < aSum) {
        bIndex++;
    }
    wins += bIndex;
}
```

A의 합도 오름차순이므로, 다음 `aSum`에서는 이전보다 작은 B의 합을 다시 확인할 필요가 없다. 두 목록을 정렬하는 비용 때문에 전체 시간복잡도는 여전히 `O(C × S log S)`이다. 현재 이분 탐색 코드도 충분히 적절하므로 **다른 방법으로도 같은 개수를 셀 수 있다**는 정도로 알아두면 된다.
