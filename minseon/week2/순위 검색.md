# 순위 검색 (프로그래머스 Lv.2)

- 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/72412?language=java

## 0. 문제 요약

지원자마다 언어·직군·경력·소울푸드 네 가지 조건과 점수가 주어진다. 각 쿼리는 조건 네 개와 기준 점수 `X`를 제시하며, 조건을 만족하고 **점수가 `X` 이상**인 지원자의 수를 묻는다. 조건의 `-`는 해당 항목을 따지지 않는다는 뜻이다.

지원자는 최대 `5 × 10⁴`명, 쿼리는 최대 `10⁵`개다.

## 사용 알고리즘 / 자료구조

- 해시맵, 조합 생성(재귀), 정렬, 이분 탐색

## 1. 문제 접근

쿼리마다 모든 지원자를 확인하면 최대 `5 × 10⁴ × 10⁵ = 5 × 10⁹`번 비교해야 한다. 쿼리가 많으므로 지원자 정보를 **미리 검색하기 좋은 형태로 저장**하기로 했다.

한 지원자의 네 조건은 각각 실제 값으로 조회될 수도 있고 `-`로 무시될 수도 있다. 따라서 지원자 한 명에 대해 각 조건을 **실제 값 / `-`** 두 가지로 선택해 `2⁴ = 16`개의 검색 키를 만든다.

```text
지원자: java backend junior pizza 150

이 지원자가 포함되는 검색 키의 일부:
javabackendjuniorpizza
java-juniorpizza
-backendjuniorpizza
----
```

각 키에 지원자의 점수를 넣는다. 같은 키에 여러 점수가 모이면 목록을 정렬한다. 쿼리에서는 조건 네 개를 같은 방식으로 이어 붙여 키를 찾고, 정렬된 점수 목록에서 **기준 점수 이상이 처음 나오는 위치**를 이분 탐색한다.

```text
정렬된 점수: [50, 80, 80, 150]
기준 점수:  80

80 이상이 처음 나오는 인덱스 = 1
전체 4명 - 앞의 1명 = 조건을 만족하는 3명
```

구현 중에는 두 가지 오류를 고쳤다.

1. `makeKey()`에서 `depth == 4`일 때 점수를 저장한 뒤 `return`하지 않아 재귀가 계속됐다. 결국 배열 범위를 벗어난 위치에 접근했다.
2. 해당 조건의 지원자가 한 명도 없는 쿼리에서는 `map.get(key)`가 `null`이다. 빈 점수 목록을 대신 넘기도록 바꿔 결과가 0명이 되게 했다.

## 2. 문제 코드

```java
import java.util.*;

class Solution {
    Map<String, List<Integer>> map = new HashMap<>();

    public int[] solution(String[] info, String[] query) {
        int[] answer = new int[query.length];

        for (String s : info) {
            String[] arr = s.split(" ");
            int score = Integer.parseInt(arr[4]);
            makeKey(arr, 0, "", score);
        }

        for (String key : map.keySet()) {
            Collections.sort(map.get(key));
        }

        int idx = 0;
        for (String s : query) {
            String q = s.replace(" and ", " ");
            String[] arr = q.split(" ");

            String key = "";
            for (int i = 0; i < 4; i++) {
                key += arr[i];
            }

            List<Integer> scores = map.getOrDefault(key, Collections.emptyList());
            int cnt = scoreBound(scores, Integer.parseInt(arr[4]));
            answer[idx++] = cnt;
        }

        return answer;
    }

    int scoreBound(List<Integer> scores, int score) {
        int left = 0;
        int right = scores.size();

        while (left < right) {
            int mid = (left + right) / 2;

            if (scores.get(mid) < score) {
                left = mid + 1;
            } else {
                right = mid;
            }
        }

        return scores.size() - left;
    }

    void makeKey(String[] arr, int depth, String key, int score) {
        if (depth == 4) {
            map.putIfAbsent(key, new ArrayList<>());
            map.get(key).add(score);
            return;
        }

        makeKey(arr, depth + 1, key + arr[depth], score);
        makeKey(arr, depth + 1, key + "-", score);
    }
}
```

### 코드 구현 흐름

| 순서 | 코드·함수 | 하는 일 |
| --- | --- | --- |
| 1 | `solution()`의 `info` 반복문 | 각 지원자의 조건과 점수를 분리한다. |
| 2 | `makeKey()` | 네 조건마다 실제 값 또는 `-`를 골라 16개 키에 점수를 넣는다. |
| 3 | `Collections.sort()` | 키별 점수 목록을 정렬해 점수 조건을 빠르게 검사할 준비를 한다. |
| 4 | `solution()`의 `query` 반복문 | `" and "`를 제거하고 네 조건을 이어 붙여 검색 키를 만든다. |
| 5 | `getOrDefault()` | 해당 키가 없으면 빈 목록을 사용해 0명으로 처리한다. |
| 6 | `scoreBound()` | 기준 점수 이상인 첫 위치를 찾고, `전체 수 - 위치`를 반환한다. |

## 3. 새롭게 배운 내용

### 왜 한 지원자에게 16개의 키가 필요할까?

쿼리는 네 조건 각각에 대해 구체적인 값을 쓰거나 `-`를 쓸 수 있다. 예를 들어 `java backend junior pizza`인 지원자는 `java backend junior pizza` 쿼리에도, `java - junior pizza` 쿼리에도, `- - - -` 쿼리에도 포함되어야 한다.

조건 하나당 선택이 두 가지이고 조건이 네 개이므로 `2 × 2 × 2 × 2 = 2⁴ = 16`개다. `makeKey()`는 재귀 단계마다 **실제 값으로 가는 가지와 `-`로 가는 가지**를 만든다.

### `depth == 4`에서 왜 `return`해야 할까?

`arr[0]`부터 `arr[3]`까지가 네 조건이고 `arr[4]`는 점수다. 네 조건을 모두 선택한 `depth == 4`에서는 완성된 키에 점수를 넣고 **그 재귀 호출을 끝내야 한다.**

`return`이 없으면 아래의 재귀 호출로 계속 내려가 `depth`가 5가 된다. 그다음 `arr[5]`를 읽으려 하므로 `ArrayIndexOutOfBoundsException`이 발생한다. 재귀의 종료 조건에는 결과 처리뿐 아니라 **실제 종료**가 필요하다.

### 키가 없을 때 왜 빈 목록을 넘길까?

어떤 쿼리와 일치하는 지원자는 아예 없을 수 있다. 이때 `map.get(key)`는 `null`이고, 그대로 `scoreBound()`에 넘기면 `scores.size()`에서 오류가 난다.

```java
List<Integer> scores = map.getOrDefault(key, Collections.emptyList());
```

키가 없으면 크기가 0인 목록을 사용한다. `scoreBound()`는 반복문을 건너뛰고 `0 - 0 = 0`을 반환한다. `Collections.emptyList()`는 여기서 읽기만 하므로 사용할 수 있다.

### 왜 `scores.size() - left`가 정답일까?

`scoreBound()`는 **점수가 `score` 이상인 첫 위치**를 찾는다. 그 앞의 `left`명은 기준 점수보다 낮고, 나머지가 기준 점수 이상이다.

```text
점수:       [50 | 80, 80, 150]
인덱스:       0 |  1   2    3
기준: 80      낮음 | 기준 이상
                  ↑
                left = 1

전체 4명 - 기준보다 낮은 1명 = 3명
```

`scores.get(mid) < score`일 때는 `mid`까지가 기준보다 낮으므로 `left = mid + 1`로 옮긴다. 같은 점수는 “이상”에 포함되어야 하므로 `scores.get(mid) == score`일 때는 왼쪽 경계 후보로 남겨 둔다.

## 4. 처음 보는 문제에서의 사고 흐름

### “조건을 만족하는 사람이 몇 명인가?” → 왜 미리 키를 만들까?

가장 단순한 방법은 쿼리 하나마다 모든 지원자의 네 조건을 비교하는 것이다. 하지만 지원자 최대 `5 × 10⁴`명과 쿼리 최대 `10⁵`개를 곱하면 최대 `5 × 10⁹`번 검사해야 한다.

따라서 **쿼리를 처리할 때 사람을 다시 훑지 않도록**, 지원자 정보를 조건별 검색 키 아래에 미리 모은다. 쿼리가 많고 같은 조건을 반복 조회한다는 점이 전처리를 떠올릴 단서다.

### “조건을 무시할 수 있는 `-`가 있다” → 왜 재귀로 16개 키를 만들까?

쿼리의 어느 위치에든 `-`가 올 수 있다. 한 지원자가 어떤 쿼리에 포함되는지 생각하면, 네 조건마다 **실제 값을 유지하거나 `-`로 바꾸는 선택**이 필요하다.

이 선택을 중첩 `for`문 네 개로 작성할 수도 있다. 하지만 “한 조건을 선택하고 다음 조건으로 이동”하는 규칙이 반복되므로 재귀로 작성했다. 경우의 수가 지원자당 `2⁴ = 16`개로 작아, 모든 키를 미리 만들어도 감당할 수 있다.

### “점수 `X` 이상” → 왜 정렬과 이분 탐색일까?

조건 키로 지원자 목록을 찾은 뒤에도, 점수를 매번 처음부터 끝까지 세면 쿼리마다 많은 사람을 다시 확인해야 한다. 점수를 정렬하면 **`X` 미만은 앞쪽, `X` 이상은 뒤쪽**으로 모인다.

그러면 필요한 것은 모든 점수를 하나씩 확인하는 일이 아니라 **두 구간이 갈리는 첫 위치**를 찾는 일이다. 정렬된 목록에서 그 경계를 빠르게 찾기 위해 이분 탐색을 선택한다. 경계 뒤의 원소 개수는 `목록 크기 - 경계 인덱스`다.

즉, 이 풀이에서 알고리즘을 고르는 순서는 다음과 같다.

```text
쿼리마다 전체 지원자를 검사하기에는 입력이 큼
→ 조건별 검색 키를 미리 만들기

네 조건마다 실제 값 또는 '-'가 가능함
→ 각 지원자의 16개 키를 재귀로 생성

키를 찾은 뒤에도 점수 X 이상을 반복해서 세어야 함
→ 키별 점수를 정렬하고 이분 탐색으로 경계 찾기
```

## 5. 시간복잡도 / 공간복잡도

지원자 수를 `N`, 쿼리 수를 `Q`라고 하면 `N ≤ 5 × 10⁴`, `Q ≤ 10⁵`이다.

- 지원자별 키 생성: 한 명당 `2⁴ = 16`개이므로 `O(16N)`.
- 키별 점수 목록 정렬: 모든 목록에 대한 상한은 `O(16N log N)`.
- 쿼리 처리: 키 조회와 이분 탐색으로 쿼리당 평균 `O(log N)`, 전체 `O(Q log N)`.
- **전체 시간복잡도: 평균적으로 `O(16N log N + Q log N)`**.
- **공간복잡도: `O(16N)`** — 한 지원자의 점수가 최대 16개 목록에 저장된다.

최대 입력에서 저장하는 점수는 `16 × 5 × 10⁴ = 8 × 10⁵`개다. `log₂(5 × 10⁴)`는 약 16이므로 정렬·탐색의 규모를 가늠할 수 있다. 실제 시간은 문자열 처리, 리스트 정렬, 해시 조회 비용도 포함하므로 `10⁸` 같은 숫자만으로 통과 여부를 단정하지 않는다.

## 6. 엣지 케이스

- 조건에 맞는 지원자가 전혀 없으면 키가 맵에 없으므로 빈 목록을 사용해 `0`을 반환한다.
- 점수가 기준 점수 `X`와 같다면 “`X` 이상”에 포함한다.
- `- - - -` 쿼리에서는 모든 지원자의 점수가 모인 키를 조회한다.
- 같은 조건과 점수를 가진 지원자가 여러 명이라면 리스트에 각각 저장해 인원수를 모두 센다.
- 재귀는 네 조건을 다 고른 `depth == 4`에서 반드시 끝낸다.

## 7. 한줄평

`-`가 있는 조건을 지원자마다 미리 펼쳐 저장하고, 점수는 정렬해 경계만 찾으니 많은 쿼리를 빠르게 처리할 수 있었다.

## 8. 더 나은 풀이와 코드 개선

현재 풀이의 핵심 구조는 효율성 테스트에 잘 맞는다. 코드를 조금 간결하게 쓰고 싶다면 `makeKey()`에서 다음처럼 리스트 생성과 점수 추가를 한 줄로 합칠 수 있다.

```java
map.computeIfAbsent(key, k -> new ArrayList<>()).add(score);
```

이는 키가 없을 때만 새 리스트를 만들고, 그 리스트에 점수를 추가한다. 다만 새로운 문법이 더 낯설다면 지금처럼 `putIfAbsent()`와 `get()`을 나누어 쓰는 편이 설명하기 쉽다.

또 `map`이 객체의 필드이므로 같은 `Solution` 인스턴스에서 `solution()`을 여러 번 호출하는 상황까지 고려한다면 시작할 때 `map.clear()`로 이전 호출의 데이터를 비울 수 있다. 제출한 문제의 알고리즘 자체를 바꿔야 하는 사항은 아니다.

## 9. 비슷한 문제에 적용하기

| 문제에서 보이는 특징 | 떠올릴 방법과 이유 |
| --- | --- |
| 같은 데이터에 대한 조건 검색을 아주 많이 반복 | 조회할 때 전부 훑지 않도록 전처리·인덱싱 |
| 항목마다 “선택하거나 무시”하는 조건이 소수 개 | 가능한 조건 키를 미리 조합해 저장 |
| 한 조건에 해당하는 값 중 기준 이상인 개수를 반복 조회 | 값들을 정렬한 뒤 첫 경계를 이분 탐색 |
| 검색 결과가 없을 수도 있음 | 빈 결과를 정상적인 경우로 처리 |

핵심은 **쿼리가 무엇을 반복해서 요구하는지 먼저 찾고**, 그 값을 빠르게 답할 수 있도록 지원자 정보를 미리 구성하는 것이다.
