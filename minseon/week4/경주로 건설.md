# 경주로 건설 (프로그래머스 Lv.3)

- 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/67259

## 0. 문제 요약

`N × N` 격자의 `(0, 0)`에서 `(N-1, N-1)`까지 벽을 피해서 경주로를 만든다. 상하좌우로 한 칸 연결하는 **직선 도로는 100원**이고, 이동 방향이 바뀌어 **코너가 생기면 500원이 추가**된다. 경주로를 건설하는 최소 비용을 반환한다. `N`은 최대 25이며 도착 가능한 길은 항상 존재한다.

## 사용 알고리즘 / 자료구조

- 다익스트라, 우선순위 큐, 방향별 최소 비용 배열

## 1. 문제 접근

### 첫 번째 접근: 일반 BFS로 도착 비용 모으기

처음에는 일반 BFS로 격자를 이동하면서 도착점에 도달할 때마다 비용을 `list`에 넣고, 마지막에 정렬해 가장 작은 값을 고르려 했다. 방향이 바뀌었는지는 `h`, 방문 여부는 `visited[r][c]`로 관리했다.

```java
boolean[][] visited = new boolean[n][n];
boolean h = false;

if (r == n - 1 && c == n - 1) list.add(money);
// ...
if (board[nr][nc] == 1 || visited[nr][nc]) continue;
```

이 접근에서 확인한 문제는 다음과 같다.

| 처음 코드에서 확인할 부분 | 왜 문제가 되는가 | 수정 방향 |
| --- | --- | --- |
| `nr < 0 && nc < 0 && nr >= n && nc >= n` | 한 좌표가 동시에 범위 아래와 위일 수 없다. | 네 조건 중 하나라도 참이면 건너뛰도록 `||` 사용 |
| `money += ...` | 한 칸에서 뻗는 네 후보가 같은 `money`를 이어서 사용한다. | 후보마다 `nextMoney`를 새로 계산 |
| 코너일 때 `+500` | 코너가 생기는 이동에도 직선 도로 100원이 필요하다. | 방향 변경 시 `100 + 500 = 600` 추가 |
| BFS 전체가 공유하는 `h` | 한 경로에서 방향을 바꾸면 다른 경로의 방향에도 영향을 준다. | 각 탐색 상태에 이전 방향 저장 |
| `visited[r][c]` | 같은 칸에 도착해도 들어온 방향과 누적 비용에 따라 이후 결과가 달라진다. | `cost[r][c][direction]`에 최소 비용 저장 |
| 도착 비용을 모두 모아 정렬 | 앞에서 `visited`로 버린 경로는 나중에 정렬해도 되살릴 수 없다. | 더 싼 상태를 발견할 때마다 다시 탐색 |

특히 **거리두기 문제의 BFS와 달리 이동 비용이 일정하지 않다**는 점이 가장 큰 차이다. 먼저 도착한 경로가 가장 싼 경로라는 보장이 없으므로, 누적 비용이 작은 상태부터 꺼내는 다익스트라로 바꿨다.

### 최종 접근: 칸과 방향을 하나의 상태로 보기

큐에 `(행, 열, 이전 이동 방향, 현재까지의 비용)`을 넣는다. 현재 방향으로 한 칸 더 가면 100원, 이전 방향과 다른 방향으로 가면 600원을 더한다. 새 비용이 그 **칸·방향 조합의 기존 최소 비용**보다 작을 때만 갱신하고 큐에 넣는다.

```text
현재 상태 (r, c, direction, money)
  → 다음 칸 (nr, nc), 새 방향 i, 새 비용 nextMoney 계산
  → nextMoney < cost[nr][nc][i]이면 갱신 후 탐색
```

출발점은 아직 이전 이동 방향이 없으므로 `direction = -1`이다. 모든 이동 비용이 양수이기 때문에, 우선순위 큐에서 도착점을 **처음 꺼냈을 때의 비용**이 최소 비용이다.

## 2. 문제 코드

```java
import java.util.*;

class Solution {
    public int solution(int[][] board) {
        int n = board.length;

        int[] dr = {0, 0, 1, -1};
        int[] dc = {1, -1, 0, 0};

        int[][][] cost = new int[n][n][4];
        for (int r = 0; r < n; r++) {
            for (int c = 0; c < n; c++) {
                Arrays.fill(cost[r][c], Integer.MAX_VALUE);
            }
        }

        PriorityQueue<int[]> pq =
                new PriorityQueue<>((a, b) -> Integer.compare(a[3], b[3]));

        pq.offer(new int[]{0, 0, -1, 0});

        while (!pq.isEmpty()) {
            int[] cur = pq.poll();
            int r = cur[0];
            int c = cur[1];
            int direction = cur[2];
            int money = cur[3];

            if (direction != -1 && money > cost[r][c][direction]) {
                continue;
            }

            if (r == n - 1 && c == n - 1) {
                return money;
            }

            for (int i = 0; i < 4; i++) {
                int nr = r + dr[i];
                int nc = c + dc[i];

                if (nr < 0 || nr >= n || nc < 0 || nc >= n) continue;
                if (board[nr][nc] == 1) continue;

                int nextMoney = money;
                if (direction == -1 || direction == i) {
                    nextMoney += 100;
                } else {
                    nextMoney += 600;
                }

                if (nextMoney < cost[nr][nc][i]) {
                    cost[nr][nc][i] = nextMoney;
                    pq.offer(new int[]{nr, nc, i, nextMoney});
                }
            }
        }

        return -1;
    }
}
```

### 코드 구현 흐름

| 순서 | 함수·코드 | 역할 |
| --- | --- | --- |
| 1 | `solution()`의 `cost` 초기화 | 각 칸에 네 방향으로 도착하는 최소 비용을 처음에는 무한대로 둔다. |
| 2 | `pq.offer({0, 0, -1, 0})` | 방향이 없는 출발 상태를 넣는다. |
| 3 | `pq.poll()` | 아직 처리할 상태 중 비용이 가장 작은 것을 꺼낸다. |
| 4 | 오래된 상태 검사 | 같은 칸·방향에 이미 더 싼 경로가 발견되었다면 건너뛴다. |
| 5 | 네 방향 탐색 | 범위와 벽을 확인하고, 직선·코너 여부에 따라 새 비용을 계산한다. |
| 6 | `nextMoney < cost[nr][nc][i]` | 더 싼 경로일 때만 비용을 갱신하고 다음 상태로 넣는다. |
| 7 | 도착점 검사 | 비용순으로 꺼낸 첫 도착 상태의 비용을 반환한다. |

## 3. 새롭게 배운 내용

### 일반 BFS와 다익스트라의 차이

일반 BFS는 모든 이동의 비용이 같을 때 **이동 횟수가 적은 순서**로 상태를 확인한다. 이 문제에서는 직선과 코너의 비용이 달라 이동 횟수가 적어도 총비용은 더 클 수 있다. 실제 문제 예시에서는 직선 도로 12개와 코너 4개인 경로가 `12 × 100 + 4 × 500 = 3,200`원인데, 직선 도로 10개와 코너 5개인 경로는 `10 × 100 + 5 × 500 = 3,500`원이다. 최소화할 값이 이동 횟수가 아닌 **누적 비용**이므로 비용순 탐색이 필요하다.

### `direction`은 어디를 향하는 방향일까?

`direction`은 현재 칸에 **들어올 때 방금 이동한 방향**이고, 반복문의 `i`는 **지금 가려는 방향**이다.

| 인덱스 | `dr[i]`, `dc[i]` | 이동 방향 |
| --- | --- | --- |
| `0` | `(0, 1)` | 오른쪽 |
| `1` | `(0, -1)` | 왼쪽 |
| `2` | `(1, 0)` | 아래 |
| `3` | `(-1, 0)` | 위 |

예를 들어 오른쪽으로 이동해 `(0, 1)`에 왔다면 `direction = 0`이다. 다음에도 오른쪽(`i = 0`)이면 100원, 아래(`i = 2`)이면 600원을 더한다. 다음 상태에는 **이번에 이동한 방향 `i`**를 넣으므로, 그 상태에서 다시 이전 방향으로 사용할 수 있다. 출발점의 `-1`은 아직 이동한 적이 없다는 뜻이며 첫 이동에는 코너가 없다.

### 같은 칸이어도 방향별로 비용을 저장하는 이유

같은 `(r, c)`에 가로 방향으로 들어온 경우와 세로 방향으로 들어온 경우를 생각해 보자. 다음에 아래로 이동해야 한다면 가로로 들어온 경로에는 코너가 생기고, 세로로 들어온 경로에는 생기지 않는다. 따라서 `visited[r][c]`나 `cost[r][c]` 하나로 두 경로를 합치면 안 된다. 다음 이동의 비용까지 결정할 수 있는 상태는 **`(r, c, direction)`**이다.

### 왜 `nextMoney`가 필요한가?

`money`는 현재 칸까지의 **공통 비용**이고, 네 방향은 그 칸에서 갈라지는 **서로 다른 후보**다. `for`문 안에서 `money += ...`로 바꾸면 첫 후보에서 늘어난 비용이 두 번째 후보에도 남는다. 방향마다 `nextMoney = money`로 시작해 독립적으로 계산한다. 이전 코드의 `h`도 같은 이유로 모든 후보가 공유할 수 없고, 각 큐 항목에 넣어야 한다.

### 최소 비용 배열과 오래된 큐 항목

더 싼 경로를 찾으면 `cost[nr][nc][i]`를 갱신하고 우선순위 큐에 새 항목을 넣는다. 예전에 넣은 비싼 항목이 큐에 남아 있을 수 있으므로, 꺼냈을 때 `money > cost[r][c][direction]`이면 건너뛴다. 이 배열은 단순 방문 표시가 아니라 **지금까지 발견한 해당 상태의 최소 비용**이다.

## 4. 처음 보는 문제에서의 사고 흐름

### ① 무엇을 최소화하나?

먼저 격자 문제라는 사실보다 **최소화 대상이 이동 칸 수인지, 건설 비용인지**를 본다. 이 문제는 비용이 목표다. 모든 이동이 같은 값이면 일반 BFS를 떠올릴 수 있지만, 직선과 코너의 비용이 다르므로 먼저 일반 BFS로 답을 확정해도 되는지 의심해야 한다.

### ② 다음 비용을 계산하려면 무엇을 기억해야 하나?

현재 위치 `(r, c)`만 알면 다음 비용을 계산할 수 있을까? 같은 칸에서 아래로 움직여도, 그 칸에 오른쪽으로 들어왔으면 코너가 생기고 아래로 들어왔으면 직선이다. 따라서 위치만으로는 부족하다. **이전 이동 방향을 상태에 추가**한다. 방향이 이동 비용에 영향을 준다는 문장이 이 결정을 내리는 단서다.

### ③ 한 번 방문한 칸을 버려도 되나?

다른 방향에서 오거나 나중에 더 싼 비용으로 오면 결과가 달라질 수 있다. 그러므로 `visited[r][c]`로 첫 방문만 허용하지 않는다. 대신 `cost[r][c][direction]`과 새 비용을 비교해, **더 좋아진 상태만 다시 탐색**한다.

### ④ 어떤 순서로 탐색할까?

일반 큐의 처리 순서는 먼저 넣은 순서이지 최소 비용 순서가 아니다. 누적 비용이 작은 상태부터 처리하려면 우선순위 큐를 쓴다. 모든 이동 비용이 양수이므로, 도착점을 처음 꺼냈을 때 그 비용을 정답으로 확정할 수 있다.

```text
비용이 서로 다르다
→ 위치만으로는 다음 비용을 알 수 없으니 방향도 상태에 넣는다
→ 칸·방향별로 더 싼 비용이 나오면 갱신한다
→ 비용이 작은 상태부터 꺼내는 다익스트라를 사용한다
```

## 5. 시간복잡도 / 공간복잡도

`N`을 한 변의 길이라고 하자. `(행, 열, 방향)` 상태는 최대 `4N²`개이고, 각 상태에서 최대 네 방향을 확인한다.

- 시간복잡도: `O(N² log N²)` — 상태와 이동 방향의 개수 4는 상수이며, 우선순위 큐를 사용한 다익스트라의 비용이다.
- 공간복잡도: `O(N²)` — 방향별 최소 비용 배열과 우선순위 큐다.
- 최대 `N = 25`라면 관리할 상태는 `4 × 25² = 2,500`개, 방향 확인은 상태당 최대 4번이다. 우선순위 큐 연산을 포함해도 흔히 참고하는 `10⁸`회 규모보다 작다. 다만 `10⁸`은 통과를 보장하는 절대 기준이 아니다.

## 6. 엣지 케이스

- 출발점에서는 이전 이동 방향이 없으므로 첫 이동은 100원만 더한다.
- 방향이 바뀌는 이동은 500원이 아니라 **100원 + 추가 500원 = 600원**이다.
- 배열 범위를 벗어나는 조건은 하나만 참이어도 건너뛴다(`||`).
- 벽은 이동할 수 없고, 같은 칸이라도 들어온 방향이 다르면 별도 상태다.
- 나중에 더 싼 경로로 같은 상태에 도착하면 비용을 갱신하고, 큐에 남은 오래된 비싼 항목은 건너뛴다.
- 문제 조건상 도착 가능한 길이 있으므로 마지막 `return -1`은 실행되지 않는다.

## 7. 한줄평

일반 BFS로 시작했지만, **비용이 다르고 이전 방향이 다음 비용을 바꾼다**는 사실을 확인하면서 `위치 + 방향`을 상태로 하는 다익스트라로 바꿀 수 있었다.

## 8. 더 나은 풀이와 코드 개선

현재 `int[]` 상태의 네 값은 각각 `cur[0]`부터 `cur[3]`까지의 위치로 구분한다. 코드가 길어지면 `r`, `c`, `direction`, `money`를 필드로 가진 작은 `State` 클래스로 표현하면 순서를 헷갈릴 위험을 줄일 수 있다. 알고리즘이나 복잡도가 달라지는 변경은 아니므로 코딩테스트에서는 현재 배열 방식도 충분하다.

`cost`를 사용하지 않고 도착 비용을 모두 저장한 뒤 정렬하는 방법은 이 문제에서 대체 풀이가 아니다. 중간에 더 좋은 경로를 버리지 않도록 **상태별 최소 비용을 관리하는 것**이 핵심이다.

## 9. 비슷한 문제에 적용하기

| 문제에서 보이는 특징 | 먼저 할 질문과 선택 |
| --- | --- |
| 모든 이동 비용이 같고 최소 이동 횟수를 구함 | 먼저 방문한 거리가 최단이므로 일반 BFS 검토 |
| 이동마다 비용이 다르고 비용이 음수가 아님 | 누적 비용이 작은 순서로 처리하는 다익스트라 검토 |
| 이전 방향·장비·남은 자원에 따라 다음 이동이 달라짐 | 위치 외에 필요한 정보를 탐색 상태에 추가 |
| 더 좋은 경로로 같은 상태에 다시 도착할 수 있음 | 단순 `visited` 대신 상태별 최소 비용을 저장·갱신 |
